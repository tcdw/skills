# agent-doc 主题文档选型与模板

`agent-doc/` 存放按任务主题拆分的检索式知识。每篇独立可读，单篇通常不超过 250 行；表格优先于长段落，结构用 ASCII 图。本文件先给选型表，再给每篇模板。

## 文档边界

写进 `agent-doc/README.md` 的约定，明确每层文档的职责，防止知识放错位置：

- `AGENTS.md`：稳定入口、仓库规则、命令和主题目录。
- `agent-doc/` 正文：当前实现的可检索知识与故障处理。
- `design/`：产品与技术设计原文，只归档，不作为运行状态记录。
- 测试：可执行行为契约；文档与测试冲突时，先核对源码和最近迁移，再修正文档或实现。

## 主题选型表

按调查结果选配，宁缺毋滥——没有对应内容的主题不建空文档：

| 仓库信号 | 建议文档 |
| --- | --- |
| 任何仓库（必写） | `README.md`、`architecture.md`、`verification.md` |
| 有数据库 / ORM / 持久化存储 | `data-layer.md` |
| 有集中配置文件或配置 schema | `configuration.md` |
| 有服务进程、部署、运维排障 | `operations.md` |
| 领域术语密集（外部 API 概念、黑话） | `glossary.md` |
| 有一段复杂的核心业务流程 | `<domain>-flow.md`（如 `telegram-agent-flow.md`） |
| 前端文件路由（Expo Router / Next 等） | `routes.md` |
| 有特殊的实机 / 环境调试手段 | `debugging.md`（如 `mobile-debugging.md`） |
| 静态资源有渲染坑（看板娘、图标管线） | `assets-and-images.md` |
| 有进行中的大型重构 / 迁移 | `plan` 文档或目录（如 `v3-plan/`、`bun-to-node-migration.md`） |
| 有沉淀的设计原文 | `design/` 归档 |
| 需要留下跨 session 的开发记录 | `devlogs/`（按 `YYYYMMDD-主题.md` 命名） |

## README.md 模板

```markdown
# Agent Documentation

本目录存放面向 AI agent 的项目知识。根目录 [../AGENTS.md](../AGENTS.md) 是统一入口；这里的文档按任务主题拆分，避免每次加载完整设计。

## 使用方式

1. 先读 [../AGENTS.md](../AGENTS.md) 的项目约束与「Where to Look」。
2. 根据任务只读取相关主题文档。
3. 以当前源码、迁移和配置 schema 为最终事实；设计文档用于理解范围与意图。
4. 行为或运维契约改变时，同步更新对应主题文档和本索引。

## 快速入口

| 任务 | 文档 |
| --- | --- |
| <任务动词短语> | [xxx.md](xxx.md) |

## 文档边界

<粘贴上方「文档边界」一节，按本仓库实际调整>
```

## architecture.md 模板

目标：让 agent 一次读完就建立完整心智模型。小项目 100 行内，复杂项目也不超过 250 行。

```markdown
# <项目名> 架构

## 进程组成 / 包依赖

<ASCII 图：进程内组件装配，或 monorepo 包依赖箭头图>

<启动 / 关闭顺序若有语义，用一段文字说明>

## 主数据流

<ASCII 图：从外部输入到最终输出的完整链路，每个节点标注关键模块路径>

## 模块职责

<目录树 + 「模块 → 职责」表格，每行一个模块>

| 模块 | 职责 |
| --- | --- |
| `src/xxx/yyy.ts` | 一句话职责 |

## 并发模型

<并发上限、互斥规则、单实例锁等，bullet 列表>

## 恢复与重试

<进程重启后的恢复语义、哪些操作绝不盲目重试>

## 信任边界

<哪些输入是不可信数据；授权由代码还是 prompt 执行；安全敏感能力如何收敛到单一边界>

## 外部依赖

| 依赖 | 用途 |
| --- | --- |
| <库名> | <一句话用途，不写版本号> |
```

小项目可裁掉「并发模型」「恢复与重试」；跨边界系统（调外部 API、处理用户输入）必须有「信任边界」。

## verification.md 模板

只写**本仓库特有**的验证手段；通用命令在 AGENTS.md。核心是教会 agent 区分「通过了 / 被既有问题阻塞 / 未执行」。

```markdown
# 验证

本页记录本仓库特有的验证手段。通用命令见 `AGENTS.md` 的 Build/Test/Development 一节。

## 推荐验证

- <比通用检查更能暴露问题的仓库特有命令（如 bundle export、doctor 探针）>
- <验证就绪信号：启动成功的日志标志、输出中应出现的字段>

## 既有失败

不要预设 tsc / lint 处于失败状态。**先跑，再判断**。
遇到与本次改动无关的失败，在最终回复里说明是既有问题，但不要因此跳过验证。

## 结果记录

最终回复应区分三类结果：
- 已通过：<例子>
- 已执行但被既有问题阻塞：说明具体错误
- 未执行：说明原因，不要写成通过
```

若有测试套件，加一张「测试文件 → 主要契约」表；若有真实环境验收（真机、真实消息、部署），逐条列出验收点。

## 领域流程文档

当某条业务流程复杂到值得单独成篇（如 `telegram-agent-flow.md`），按「阶段顺序 + 每阶段的不变量」组织：

- 文件名用 `<domain>-flow.md`。
- 按数据流阶段分节，每节先给规则 bullet，再给关键代码路径。
- 状态机、时间窗口、降级路径等容易出错的语义重点写。

## design、devlogs 与计划文档

- `design/`：设计原文按 `YYYYMMDD 主题.md` 命名归档；AGENTS.md 与 README 索引时对含空格文件名使用 `%20` 编码链接。
- `devlogs/`：开发记录，`YYYYMMDD-主题.md`；新记录不改旧记录。
- 计划文档（`*-plan.md` 或 `plan/` 目录）：写目标、阶段、交接状态；完成后归档或删除，结论吸收进主题文档，避免与正文长期并存产生两个事实来源。
