# 文档防腐检查

## 执行边界

- 先读取仓库规则与文档索引，以当前源码、迁移、Schema 和测试为证据；不要照搬其他项目的路径、技术栈和数字。
- 区分模式：只要求扫描/检查时报告发现，不修改；明确要求修正时执行授权范围。用户选择部分步骤时只做这些步骤。
- 保留未提交改动；只编辑文档，不为迎合旧文档修改业务代码。不自动提交、启动服务、运行真实外部探针或读取本地私密配置。
- 尊重历史目录读取限制。普通审计不自动授权读取已被入口排除的历史正文；先用父级索引检查隔离规则。明确要求整理历史文档或按某份设计工作时才按需读取。
- 使用待办跟踪多阶段工作。可并行委派互不重叠的主题，但复核关键发现，不直接采信子 agent 对平台、网络或框架行为的推断。

## 1. 建立审计范围

1. 检查工作区状态，读取入口规则、当前主题索引、相关包脚本和验证说明。
2. 区分当前契约、操作手册、验证标准、历史设计/原始需求；确认默认排除目录。
3. 按主题建立“文档 → 源码/Schema → 测试”的对应关系。按需读取，排除依赖、构建产物、缓存和秘密文件。
4. 记录已覆盖、未覆盖、未运行的验证，不用少量抽查宣称逐条验证全部事实。

## 2. 按三个维度核对

### A. 代码事实

优先核对影响 agent 实现决策的契约：

- 默认值、阈值与边界运算符、条件暴露、预算、权限及副作用例外。
- 状态转换、时序、并发粒度、恢复与重试、缓存和保留策略。
- 配置合并/覆盖、触发条件、过滤与授权范围。
- 命令是否存在、路径与小节链接是否可解析、测试索引是否遗漏。
- 审计字段是初始、最新还是逐轮快照；记录存在是否真的证明成功。

跟踪到实际分支及调用方，不只用另一篇文档或代码注释作证。核对相关测试，区分“读过测试”和“测试通过”。将发现分为确认偏差、表述歧义、结构问题、待验证。

对外部平台事实有疑问时查官方材料或做安全的最小验证；不要仅因两个文件不同就宣布其中一个错误。历史设计与现状不同本身不算事实错误。

### B. Why / what 边界

采用“保留源码难表达的理由与契约，删除易漂移副本”，不要机械执行“文档不许写 what”。

保留：决策理由、跨模块不变量、授权边界、非显然例外、已知陷阱、必要命令、最小示例和验收标准。

收敛：完整工具/路由/字段清单、表数量、测试数量、依赖版本、本地配置当前值、多页重复维护的行为细节。把完整清单链接到权威模块及检索符号，不让 agent 为理解一个关键例外阅读整套源码。

将示例标为假设，不把某台机器的配置当项目默认值。保留真正有语义的阈值、限制和错误码，不删除所有数字。

### C. Agent 理解与导航

- 按任务指向当前主题，不默认引入历史设计。
- 区分当前行为、历史决策、未实施计划与本次执行指令。
- 检查公式是否依赖未说明的前置步骤，绝对表述是否漏掉作用域或例外。
- 使用具体小节、源码路径和符号，避免裸文件名歧义、重复近似入口和循环跳转。
- 保持渐进读取：入口讲规则与导航，主题页讲契约与理由，源码提供细节。

## 3. 报告发现

按严重程度报告高价值问题，每项给出文档位置与原陈述、源码/测试证据、误导风险和最小建议。结构问题给出具体重复段落或导航证据，不为凑数量报告措辞偏好。

标注检查范围、历史排除项及验证状态。建议依次执行下面三步；没有修改授权时停在报告。

## 4. 按授权执行三步修正

### 第一步：修正事实和作用范围

最小修改已证实错误，检查其他当前主题页是否保留同一矛盾。补充条件、粒度、时序和例外，不扩大行为承诺，不重构业务代码。

### 第二步：在父级隔离历史资料

把完整规则集中到父级文档入口；仓库总入口保留简短规则或指向它的导航，不在每篇历史文档重复免责声明。

按仓库路径调整模板：

> 历史目录中的文档默认不读取、不检索，也不作为当前行为、约束或待办的依据。仅当用户明确指定参考某份设计、按该设计实施，或要求追溯历史决策时，才按需读取。普通功能需求不自动启用历史资料。历史执行指令不自动生效；实施前必须核对当前源码。

- 将普通任务索引中的历史链接移到单独的按需历史索引，保留当前主题入口。
- 用户授权清理逐篇声明时，删除顶部重复免责声明，保留原始正文、历史阶段记录及决策证据，不把历史原文改写成当前实现。
- 不新增逐篇 banner 解决全局检索规则问题。父级规则已清晰且导航一致时不重复改动。

### 第三步：去重和收敛职责

- 架构页解释分层、状态所有权与信任边界；流程页承载跨模块调用契约；完整能力注册项指向组合根/注册模块。
- 配置页保留继承、覆盖、路径解析和隐含语义；字段类型与完整取值范围以 Schema 为准。
- 数据页保留冻结、恢复、保留与迁移陷阱；表结构和依赖版本指向源码/锁文件。
- 运维页负责如何运行、前置条件与失败处置；验证页负责检查范围和通过标准。必要命令可就地保留，其余用小节链接关联。
- 删除手写总数和私有环境状态；保留按任务选测试的导航，不以删除索引代替维护。
- 在父级入口简短记录职责分工，避免重复内容重新出现。不删除证据、验收标准或唯一操作入口。

## 5. 验证并交付

1. 阅读最终差异，确认只修改授权文档，保护无关改动和历史正文。
2. 检查本地链接、路径及 Markdown 小节锚点；区分代码 `#L` 引用与标题锚点。报告检查器不支持的语法，不把简化正则误判当断链。
3. 运行 `git diff --check` 和仓库要求的格式/静态检查。仅文档去重不默认跑完整行为测试；涉及行为陈述修正时按需要运行相关测试。遵守仓库更严格的验证要求。
4. 格式器不覆盖 Markdown 时，不把 lint 成功说成 Markdown 已全面验证。修复检查失败时避免全仓库自动修复伤及无关文件。
5. 汇总改动、保留项、通过项与未验证项，说明是否改业务代码及提交状态。

## 自检场景

- “扫描文档”：只报告证据，不改文件。
- 根入口排除历史目录：先核对父级规则与导航，不擅读历史正文。
- 两篇文档对 Docker/数据库行为矛盾：核对实现与权威证据，不凭子 agent 断言修文档。
- “只做 1 和 2”：修事实、父级历史隔离，不顺带去重。
- 文档有关键阈值和完整 API 清单：保留阈值语义、链接清单，不以“只说 why”全部删除。
- “统一历史声明”：在父级维护规则并整理导航，不给每篇添加同样 banner。
